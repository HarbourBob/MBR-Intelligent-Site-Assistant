A self-hosted conversational site search. No external APIs are used for search, and visitor queries never leave your server.

== Description ==

MBR Intelligent Site Assistant gives your WordPress site a conversational search widget. Uses BM25 ranking with intent matching, synonym expansion, and a chat-style interface.

A comprehensive User Guide (PDF) is bundled in the ZIP file.

Key features:

* Self-hosted — no API keys and no external services on the visitor path. Ranking, PDF extraction and snippets all run locally; the only outbound request is the optional plugin update check.
* Works on virtually every WordPress host -> pure PHP. The only requirement beyond WordPress itself is the mbstring extension, which ships with almost all PHP installs; PDF indexing additionally uses zlib.
* Intent matching for common questions (contact, pricing, services).
* Synonym expansion so "WP" finds "WordPress".
* Porter stemming so "building" matches "build".
* Query log and feedback for tuning.
* Catppuccin Mocha dark UI.

== Installation ==

1. Upload the plugin folder to `/wp-content/plugins/`.
2. Activate through the 'Plugins' menu in WordPress.
3. Go to MBR Site Assistant -> MBR ISA Diagnostics to verify installation.

== Changelog ==

= 0.9.21 =
Ten low-severity findings from an external re-test of 0.9.20. Nothing about indexing, ranking, the visitor path or the schema changes, so **no reindex is required**.

* **Fixed: feedback recording was not atomic.** The endpoint read the `feedback` column, checked it was still NULL, and then wrote it, with nothing holding the row in between — so two submissions arriving at the same moment could both pass the check, and the second would overwrite the first. That is the "one rating per answer" rule introduced in 0.9.7 failing at precisely the moment it is meant to apply. The window is small and the prize is changing your own rating, so this is an integrity fault rather than a vulnerability, but the fix costs nothing: the write now carries `AND feedback IS NULL` in its WHERE clause, so the database decides which of the two arrived first. The losing request gets a 409, which the widget already treats as success.

* **Fixed: the documentation said the inline-asset extraction was finished, and four blocks remained.** 0.9.20 moved the Diagnostics CSS and JavaScript into real files and then stated in five separate places that the work was complete — while the intents, synonyms and Appearance screens still carried 417 lines of inline CSS and script between them, rather more than had actually been extracted. The practical cost was for anyone who read that and set a strict admin Content-Security-Policy: the Appearance screen's live preview would have gone silently dead and three screens unstyled, having been told the opposite. The extraction is now genuinely complete. The three remaining `<style>` blocks moved into `assets/css/mbr-isa-admin.css`, and the Appearance screen's script into a new `assets/js/mbr-isa-appearance.js`, with its preset list and glass bounds passed through `wp_localize_script()` exactly as the Diagnostics script already did. No admin screen carries inline CSS or script now.

* **Fixed: the reindex button pointed at controls that had moved.** The Status tab described itself as indexing "the post types selected below". The tab split put those checkboxes on the Content tab, so the single instruction on that screen directed you somewhere that no longer existed.

* **Fixed: the translation template had not been regenerated since 0.9.10.** The 0.9.8 audit found that no `.pot` shipped at all, so `load_plugin_textdomain()` pointed at nothing; that was fixed in 0.9.10 and has been quietly regressing ever since, leaving every string added across ten releases untranslatable. The visible casualty was the new tab strip — only Status and Feedback existed as msgids, picked up from elsewhere in the plugin, so a translated site showed two translated tabs and five English ones. Regenerated against 0.9.21: 325 strings, current line references, translator comments carried through.

* **Fixed: the PDF extractor collapsed whitespace twice.** Two identical passes sat three lines apart with nothing between them. The first was redundant work over the full extracted text of every PDF, and the second is strictly better because it has the byte-wise fallback the first lacked. Its comment also pointed at a "contents-page rule below" that is not in that function. This predates 0.9.20 and was found while verifying the fix immediately below it.

* **Fixed: a stylesheet rule that matched nothing.** `[id^="mbr-isa-synonym-"]` was added in 0.9.20 alongside the intents anchors, but the synonyms screen uses that string as a class name and has no matching id, so the rule was inert — and it read as though the synonyms screen had the anchored-save behaviour, which it did not. Rather than delete the selector, the synonyms screen now behaves the same way the intents screen has since 0.9.20: saving returns you to the card you were working on, or to the blank add form after an addition. The same annoyance applied there, and the same fix suits it.

* **Fixed: four dead `global $wpdb;` declarations** left behind by the tab split. Harmless at runtime, and misleading in the way an unused import is.

* **Changed:** `includes/class-mbr-isa-frontend.php` was the only tab-indented file in the tree and now uses four spaces like the other twenty. Whitespace only.

= 0.9.20 =
An admin usability release. Nothing about indexing, ranking or the visitor path changes, so **no reindex is required** and the schema is unchanged.

* **The Diagnostics screen is now tabbed.** It had grown a section at a time into one long scroll of unrelated controls, which made the thing you wanted hard to find and the thing you did not want easy to change by accident. There are now seven tabs: Status, Content, Alt Text, Privacy, Widget, Feedback and Testers. Each renders on its own, so only the active tab's queries run — the feedback statistics and the alt text worklist are the expensive ones, and neither is touched unless you are looking at it. Saving any setting returns you to the tab that owns it.

* **Adding an intent no longer throws you back to the top of the page.** Saving redirected to the top of the intents screen, so adding several intents in a row meant scrolling to the bottom again each time. A save now returns to the card it concerns: the blank "add" form after an addition, ready for the next one, or the edited intent's own card otherwise. Validation errors deliberately keep you at the top, because that is where the notice explaining the failure is, and scrolling past it would make a rejected save look as though it had simply done nothing.

* **Admin CSS and JavaScript are no longer inline.** They now ship as `assets/css/mbr-isa-admin.css` and `assets/js/mbr-isa-admin.js`, with the values PHP used to print into the markup passed through `wp_localize_script()`. Inline blocks cannot be cached and are refused outright by a strict admin Content-Security-Policy, and there were seven of them across five screens — a cost that rose with every new panel. This was the outstanding finding from the 0.9.18 re-test that was flagged as worth scheduling rather than carrying.

* The four `$_GET` display flags on the Diagnostics screen now go through `wp_unslash()` and `sanitize_key()`, closing the part of the superglobal finding that 0.9.19 left partially fixed.

= 0.9.19 =
Six low-severity fixes from an external re-test of 0.9.18. **No reindex is required** — nothing here changes what is written into the index, and there is no schema change.

* **Fixed: a PDF whose extracted text was invalid UTF-8 still lost all of it.** The fallback for a failed unicode whitespace pass ran against a variable the failure had already emptied, so the retry scrubbed an empty string and the document was reported as having no text layer — which is indistinguishable from a genuine scan. This is the same defect corrected elsewhere in the same function in 0.9.9; one of the two instances was missed at the time. Heavily subsetted and CID fonts are the usual source. It fails closed, so the cost was a missing result rather than a wrong one.

* **Fixed: the tokeniser decoded HTML entities twice.** Two identical `html_entity_decode()` calls sat three lines apart, the second a leftover from before the first was added. Double-encoded content was therefore decoded back into markup in the stored passage — a page displaying an escaped code sample as `&amp;lt;script&amp;gt;` was indexed as a literal `<script>`. This was never exploitable through the plugin: snippets are escaped before the highlight is injected, and the admin screens escape too. But it turned inert text into markup-shaped text inside a field the public REST response carried.

* **Fixed: `intent_supplementary_max` could not produce more than one result when the extras scored well.** The supplementary path reuses the full formatting path so that snippets, deep links and escaping cannot drift out of step — and inherited its confidence cap along with them. At high confidence `result_limit_high` defaults to 1, so the caller's maximum of 3 was unreachable, and the better the supplementary hits scored the fewer of them were shown. That is exactly the case the setting exists for. The maximum is now passed in rather than applied to what comes back.

* **Fixed: the contents-page demotion fetched every contents row in the index.** The index added in 0.9.9 stopped this being a full table scan, but the query was still unbounded in rows returned, and the loop beneath it can only use documents the query already matched. A candidate pool is 25 to 400 documents, while a documentation library can hold thousands of contents chunks — every one of them fetched into PHP on every visitor query. The query is now scoped to the matched set.

* **Changed: mbstring is declared as a requirement rather than half-guarded.** Six scattered `function_exists()` guards promised a graceful degradation the rest of the code could not deliver — the indexer, the responder and the tokeniser all call `mb_*` unconditionally, so without the extension the plugin fatalled on the first index write or the first search regardless of them. They also cost a function lookup for every token of every document. There is now a runtime check beside the PHP version guard, with an admin notice, and the guards have gone. A plugin header cannot express an extension requirement, so a notice is the only honest place to state it.

* **Changed: the full stored passage is no longer sent to every visitor.** Each result carried the whole 2,000-character passage in `excerpt` alongside the 240-character `snippet` the widget actually renders — around 6 KB of dead payload on a three-result response, on an unauthenticated endpoint, and more of each document than the snippet windowing deliberately chose to show. Nothing private was exposed, since every row has already passed the visibility gate. It is now dropped alongside the internal `extras` field.

* **Credits:** the passage chunker and the WP-CLI commands contain code contributed by James Wilson (Director of Technology, Cogora), who also carried out the 0.9.8 audit and this 0.9.18 re-test.

= 0.9.18 =
Three fixes and two additions. **A full reindex is required.**

* **Changed: high confidence now means the other results are not answers.** The dominance test compared the top score against the runner-up as a ratio, which a leading result could satisfy while the runner-up was still a good answer in its own right — and high confidence returns a single result, so that answer was ranked and then discarded. Searching a person's name showed it plainly: an image matches a name on every weighted field at once, so it ran away with the score and every document actually discussing the person vanished behind it. A runner-up at or above the medium threshold now rules out high confidence. The leader keeps its place; the rest of the list survives. The caps themselves are settable through `result_limit_high`, `result_limit_medium` and `result_limit_low`, clamped to 1-10.

* **Fixed: a mention's page label could name the page before the one it opens at.** A passage records the page it begins on, and a 250-word chunk routinely runs onto the next — so a match in its later half is a page further on. The link already corrected for that; the label did not, and named the chunk's starting page instead. A label pointing at the wrong page is worse than none, because somebody checks that page, finds nothing, and concludes the search is wrong.

* **New: further mentions in the same document.** Results collapse to one passage per document, so a term appearing three times in one PDF was only ever reachable at its best-scoring passage — the others were scored, ranked and then discarded. Those passages now appear as secondary links beneath the result, each with its own snippet, its own deep link, and its page number where the document is a PDF. The collapse itself is unchanged: confidence caps still count documents, ranking is untouched, and no long document can crowd out another. Adjacent chunks are suppressed, since a 50-word overlap means a phrase near a boundary matches twice and would otherwise show the same sentence twice. Capped at three per result, or set `passage_extras_max` to 0 for the previous behaviour.

* **Fixed: content that merely mentioned `<body>` was truncated.** 0.9.13 added a rule taking only the body of a full HTML document, which is right for a hand-built landing page pasted into the editor. But it ran on every field, including the plain text extracted from a PDF, and its second branch — an opening tag with no closing one — discarded everything before the mention. A post whose `<body>` mention fell after its prose was reduced to nothing at all; this plugin's own user guide, which documents that very rule, lost its first five pages and had the survivors renumbered from 1, which sent every PDF deep link to the wrong page. The rule now requires corroboration: a doctype or an `<html>` tag near the start, which a genuine document always carries and a passing mention never does.
* **Fixed: the Decorative button in the Alt Text Audit did not stick.** It stored empty alt text, which the scan cannot tell apart from alt text nobody has written — so the image returned to the worklist on the next scan, permanently. A separate marker now records the decision. The alt attribute is still written empty, so what a screen reader encounters is unchanged. Marked images drop out of the worklist and can be listed again to undo.
* **Fixed: WooCommerce product galleries reported as unused.** The Alt Text Audit ranks images by how many published pages display them. A gallery is stored as a bare comma-separated list of attachment IDs, which no markup or JSON pattern matches, so those images sank to the bottom of the worklist despite being on live product pages. Meta keys holding a plain ID list are now read as one, filterable through `mbr_isa_id_list_meta_keys`.

= 0.9.17 =
Attachments referenced by page builders are now found. **A full reindex is required.**

* **Fixed: page-builder layouts were invisible to the reference scan.** Whether an attachment counts as published is decided by looking for its stored relative path in post content and post meta. Page builders store their layouts as JSON, and JSON escapes forward slashes — so `2025/12/photo.png` sits in the meta as `2025\/12\/photo.png`, and the scan could never match it. This affected every attachment on every Elementor- or Bricks-built site, PDFs as well as images.
* **Elementor's thumbnail cache compounded it.** Elementor serves images from its own cache at a path containing only the filename stem and a hash, in which the original path appears nowhere at all — so even unescaping the slashes would not have found it.
* A last-resort pass now matches on the filename stem and **proves the match in PHP** rather than trusting a substring. The verifier requires the stem to sit at a path boundary followed by its own extension or a recognised derivative suffix — a WordPress size variant, `-scaled`, an image-editor revision, or an Elementor thumbnail hash.
* **The verification is what makes this safe.** A bare substring search would read a separate upload called `logo-2.png` as a reference to `logo.png`, and wrongly treat an unpublished image as published — loosening a visibility rule, which is the one thing this scan must not do. The verifier rejects that case while still recognising `logo-1024x768.png` as a genuine variant.
* The pass runs only when the precise passes have found nothing, and only for a stem of six characters or more, since a shorter one would gather half a media library as candidates for no benefit.

= 0.9.16 =
Featured images are now recognised as published usage. **A full reindex is required.**

* **Fixed: a featured image was invisible to the visibility scan.** Whether an attachment counts as published is decided by looking for its stored file path in post content and post meta. A featured image appears in neither — it is recorded as `_thumbnail_id` holding the attachment's ID, and the theme renders it from there. An image at the top of every post on a blog was therefore invisible to the scan.
* Such an image was indexed only if its `post_parent` happened to be a readable post — and that parent then became the URL the result linked to. Since `post_parent` records which editor a file was uploaded from, a blog post's featured image could be indexed under, and link to, an unrelated page.
* Featured images are now checked first, before the content and meta scans. The query is an exact match on an indexed meta key, so it costs materially less than the `LIKE` scans it precedes — cheapest test first, the same ordering already used for the parent check.
* This never mattered for PDFs, since nothing sets a PDF as a featured image, which is why the gap survived until images were indexed. It runs for all attachment types regardless, for consistency and at negligible cost.
* **Expect the indexed image count to rise after reindexing.** Any image used only as a featured image on a published post now qualifies where it previously did not.

= 0.9.15 =
Fixes image results linking to the wrong page. No schema change; a reindex is not required, though it does no harm.

* **Fixed: an image result could link to a page the image does not appear on.** The result URL preferred the attachment's `post_parent`, and `post_parent` records which editor a file was uploaded from — not which page displays it. Dragging a photo into a page once, even into a block later deleted, sets that page as the parent permanently. An image used on a blog post could therefore send the visitor to the About page: valid, readable, and entirely wrong.
* Image results now prefer a post that actually references the file, falling back to the parent only when nothing does. This is the opposite of the PDF ordering, deliberately — a PDF's parent is nearly always the page offering the download, whereas an image's parent is usually an upload artefact.
* The scan has generally already run for the visibility check and is memoised, so in the common case this costs a lookup rather than a fresh scan.
* **The choice is now deterministic.** The candidate query carries no `ORDER BY` on purpose, because an ordered `LIKE` scan must finish before the limit applies. That is fine for deciding whether a file is published, since any readable referrer settles it — but not for deciding which post to link to, where an image on several posts could otherwise link somewhere different on each request. Candidates are sorted after fetching, most recent first then by descending ID.
* Where an image is referenced from more posts than the candidate cap, the set examined can still vary. In practice that affects site furniture such as logos, where no single answer is right anyway.

= 0.9.14 =
Fixes a regression introduced in 0.9.13. **A full reindex is required.**

* **Fixed: deep links stopped scrolling to and highlighting the matched passage.** The bounded tag remover added in 0.9.13 replaced every remaining tag with a space, where `strip_tags()` had replaced it with nothing. Block-level tags are already converted to markers earlier in the process, so everything reaching that step is inline — `<strong>`, `<em>`, `<a>`, `<code>` — and those sit inside a sentence. "Uses `<strong>`WordPress`</strong>`'s own" was being indexed as "Uses WordPress 's own".
* Deep links use the Text Fragments standard, which requires the quoted run to match the rendered page exactly. A fabricated space means the browser cannot find the passage, so it loads the page and silently declines to scroll — which reads as the feature having been removed.
* Quoted phrase search across inline markup failed for the same reason, as did snippet accuracy wherever a link or bold run sat mid-sentence.
* Inline tags are now removed without inserting anything, restoring the pre-0.9.13 behaviour. Block-level separation is unaffected: those markers are added in an earlier step and still keep paragraphs apart.

= 0.9.13 =
Fixes a fault that could reduce an entire page to a few dozen characters in the index. **A full reindex is required.**

* **Fixed: one malformed tag could cost a page its entire content.** The indexer used `strip_tags()` for its final HTML removal, and `strip_tags()` has no upper bound on how far it searches for a closing bracket. A single unterminated construct — an unclosed attribute quote in a meta tag, for instance — therefore consumed everything after it. On a real 36,965-character page, 47 characters reached the index: the contents of `<title>`, and nothing else.
* The failure was completely silent. The page rendered perfectly, appeared in the document count, and returned nothing for any phrase or word that lived in its body. Quoted phrase search was simply where it became visible.
* Tag removal is now bounded: a run is treated as a tag only when it begins with a name character and closes within a plausible distance. A malformation costs the fragment it appears in rather than the remainder of the document. Script and style blocks are still removed first, so nothing executable survives the looser matching, and stray brackets become whitespace before tokenising.
* **Added: a full HTML document in `post_content` is indexed on its `<body>` only.** WordPress treats post content as a fragment, and so did the indexer — but a hand-built landing page pasted in whole carries a doctype, a head, an inline stylesheet and meta tags. On the same page that was 21,641 of 36,913 characters: more than half the "content" being CSS and metadata that can never be a useful search result, fed to the chunker as though it were prose.
* Taking the body also puts the head out of reach of everything downstream, which matters because the head is where malformed constructs tend to live.
* **Run a full reindex after updating.** Affected pages currently hold a near-empty row each; nothing corrects that until the index is rebuilt. Expect the document count to stay the same while chunks, terms and postings rise, in some cases sharply.

= 0.9.12 =
Fixes a long-standing indexing fault affecting quoted phrase search, snippet display and the term dictionary. **A full reindex is required.**

* **Fixed: HTML entities were never decoded during indexing.** WordPress stores an ampersand in post content as `&amp;` and a curly apostrophe as `&#8217;`. The indexer stripped tags but never decoded those entities, so a heading reading "Rules & Targeting" was stored as "Rules &amp; Targeting". This has been present since the tokeniser landed and affects every version of the plugin.
* **Quoted phrase search failed on any phrase containing such a character.** Searching `"Rules & Targeting"` compared the visitor's phrase against a stored passage still reading `rules &amp; targeting` and returned nothing found, on a page where the words were plainly visible. Apostrophes were affected identically, so `"See what you're getting."` failed for the same reason.
* **The term dictionary was being polluted.** With the entity left encoded, the tokeniser stripped the punctuation around it and indexed the remnant as a word: `&amp;` became the term "amp", `&#8217;` became "8217", `&nbsp;` became "nbsp". These were real searchable entries attached to a large fraction of a typical site's pages, matching queries that happened to mention them and contributing nothing.
* **Snippets shown to visitors contained raw entities.** Any passage containing an ampersand was displayed in the chat panel as literal `&amp;`.
* Entities are now decoded after tags are stripped, never before — decoding first would turn an encoded `&lt;script&gt;` back into a real tag, whereas decoding afterwards leaves it as inert literal text that is escaped again at render time.
* Decoding is also applied when comparing a quoted phrase, as well as at indexing time. That is deliberate belt and braces: rows written by an earlier version still hold encoded entities until the site is reindexed, and this makes quoted search start working the moment the files are in place.
* **A full reindex is needed** to clear the junk terms from the dictionary and to correct stored snippets. Quoted phrase search works without one; the other two do not.

= 0.9.11 =
Documentation-accuracy fix. No schema change, no reindex, no behaviour change on the front end.

* Fixed: `wp mbr-isa status` did not report image indexing. The 0.9.10 user guide documented an `Image indexing:` line in its WP-CLI section that the command never printed — the CLI was overlooked when image support was added in 0.9.9. The line is now there, and it reports the number of images actually in the index alongside the on/off state.
* The count is included because an image has two independent ways to be excluded — the visibility rule and the alt text requirement — so "on" with a count of zero is a real and fairly common state that means something specific: the setting is enabled but nothing qualifies. Reporting the switch without the count would leave that looking like a failed reindex.
* This is the same class of fault the 0.9.0 documentation audit was created to catch: the guide described what was intended and the code did something else. Every other filter, setting, option and cron hook documented in the 0.9.10 guide has now been checked against the source; this was the only discrepancy.

= 0.9.10 =
Adds an Alt Text Audit to the Diagnostics screen. No schema change and no reindex needed.

* New Alt Text Audit panel. Finds images with no alt text and ranks them by how many published pages actually display each one, so the images worth describing appear first. A logo on forty pages and a cropped duplicate nobody ever used are both "missing alt text", and an alphabetical list of three hundred files gives no way to tell them apart.
* Alt text can be written straight from the table. Each row shows a thumbnail, the filename, any existing caption or description, where the image is used, and a link to the page it appears on — enough context to write the sentence without opening anything. Enter saves, so a list can be worked through from the keyboard. Saving an image that now qualifies reindexes it immediately, so it becomes searchable at once rather than at the next full reindex.
* A "Decorative" button stores empty alt text deliberately, which is the correct answer for spacers, flourishes and borders and tells a screen reader to skip the image.
* This does not write alt text for you, by design. The plugin cannot see images — anything it generated would be inferred from the filename or the surrounding page, which is not a description, and alt text describing the wrong thing is worse for a screen reader user than none at all. Only a person looking at the picture can tell a decorative flourish from a photograph that carries meaning.
* The usage scan reads page builder layouts as well as post content. Elementor and Bricks store their layouts as JSON in postmeta rather than in post_content, so a scan reading only post_content would report almost every image on such a site as unused and invert the whole ranking. The list of meta keys is filterable via `mbr_isa_builder_meta_keys`.
* The scan is inverted rather than per-image: one pass over published content builds usage counts for every image at once, so its cost scales with the number of posts rather than with the size of the Media Library, and there is no per-file `LIKE` scan anywhere in it.
* Permission to edit alt text is `edit_post` on the attachment itself rather than `manage_options`, so an editor who can already do this in the Media Library can do it here, and somebody who cannot edit a given attachment cannot reach it through this screen.

= 0.9.9 =
Adds image indexing, off by default, and resolves the findings of an external security and code audit of 0.9.8 (nine medium, nineteen low; no critical or high). Schema change — the documents table gains a `doc_kind` column and an index on `is_contents` — applied automatically on upgrade. A full reindex is needed before images appear in results; the audit fixes need none.

* Images can now be indexed, from a new set of toggles under Content Sources. There is nothing to configure beyond those toggles and nothing is read from the image itself — an image is indexed on what a person wrote about it: its alt text, caption, description and filename, in that order of preference. JPEG, PNG, GIF, WebP and AVIF. SVG is deliberately excluded.
* Alt text is the primary signal and, by default, required. Alt text is the one field written specifically to describe what is in a picture, so images that have it are indexed and the rest are skipped. The requirement can be turned off, at which point a caption, a description or an informative filename will do instead. Either way the requirement is re-tested at search time, so deleting an image's alt text in the Media Library removes it from results without waiting for a reindex.
* Filenames are cleaned before indexing, and uninformative ones are ignored entirely. Extensions, WordPress's generated size suffixes (`-1024x768`), `-scaled` and image-editor suffixes are stripped, so `jpg` and `png` never become search terms matching every image on the site. Camera and screenshot defaults — `IMG_4821`, `DSC00042`, `Screenshot-2026-08-18-at-09.41.22`, hex blobs from media managers — are recognised and skipped, since indexing them puts high-frequency junk terms into the dictionary that can only ever produce a wrong answer.
* Image results link to the page the image appears on, not to the file. Sending a visitor to a bare `.jpg` is technically the resource that matched and a dead end as an answer. The parent post is used where there is a readable one, otherwise whichever published post the reference scan found displaying the image, and the file itself only when neither exists. Adjustable with the new `mbr_isa_image_result_url` filter.
* Clicking an image result's thumbnail opens the picture in a lightbox rather than following the link to the page. The title still goes to the page, so the thumbnail and the title now lead to different places — previously they did the same thing, which wasted the thumbnail. The lightbox traps focus, closes on Escape or a click outside, restores focus to where it came from, and shows the image's alt text with a link through to the page it appears on. It is still a real link to the image file underneath, so middle-click and open-in-new-tab behave normally and it degrades gracefully if the script fails.
* Image results carry a thumbnail and an `IMAGE` badge ahead of the title, so a picture is distinguishable from a page at a glance. An image's snippet is a single line of alt text, which as a text result reads like an empty page, so the widget leads with the picture and puts the description beneath it. The label travels as its own field in the REST response rather than being prefixed onto the title — the title is the page's own name, and the title field is indexed, so writing the word into it would make 'image' a search term attached to every picture on the site.
* Corrected a scoring fault that images would otherwise have caused. BM25 normalises by document length, and an image row holds five to ten tokens against a corpus average dominated by PDF passage chunks running to several hundred — so an image would have taken roughly a 45% scoring advantage over the page it sits on, for no reason other than being short. Image rows are now floored to the corpus average length for each field, which is the point at which the normalisation is exactly neutral: an image competes on whether its words match, not on how few of them there are. Longer-than-average descriptions are unaffected — this is a floor, not a clamp. The new `mbr_isa_image_score_weight` filter allows further tuning, and defaults to no adjustment.
* Which images qualify is a separate setting from which PDFs do, using the same three modes. They look alike and mean very different things: "every PDF in the Media Library" is a hundred documents somebody deliberately produced, while "every image in the Media Library" is several thousand files including every cropped duplicate, logo and abandoned upload.
* Content Sources reports image eligibility as two figures rather than one, because an image has two independent ways to be excluded and they need different remedies. A shortfall under "which images" is fixed on that screen; a shortfall under alt text is fixed in the Media Library, and is worth knowing about on its own terms.
* Fixed: attachment visibility answers were cached without regard to which visibility mode produced them, so tightening the setting left permissive answers in the cache for up to five minutes. Affects PDFs on all previous versions.
* Images attached to a post are re-evaluated when that post changes, as PDFs already were. A page gaining a password takes its attached images out of the index for the same reason it takes its documents out.

* Fixed: feedback ratings were rejected outright on every site with a negative UTC offset — the whole of the Americas. Query rows are written in site-local time but the expiry check compared them against a UTC clock, so a row appeared to be more than an hour old the moment it was created and every thumbs up or down came back as expired. On a positive offset, including the UK during BST, the same fault silently extended the one-hour window instead of closing it.
* Fixed: an undefined variable on the public search path. `pages_before_match()` referred to a `$phrase` its signature never declared, which emitted a PHP warning for every PDF result whose passage crossed a page boundary — a common case, since passages are 250 words and pages hold more. On a site with `display_errors` on, that warning was written ahead of the REST response, corrupting the JSON so the widget reported a failure, and disclosing the plugin's absolute path on the server. It also meant quoted searches on PDFs quietly fell back to token scoring and opened at the wrong page.
* Fixed: an undefined array key on every shortcode render, with the same warning-in-the-page-body consequence. `render_shortcode()` never supplied the `extra_attrs` key that only the floating widget sets.
* Fixed: a malformed PDF could hang the request that uploaded it. Neither the depth limit nor the page-count limit bounded a cyclic page tree — a node whose children point back at it branches two ways per level and adds nothing to the page list on the way, so both guards were unreachable. Any user able to upload a file could trigger it, and it broke the administrator's next reindex too.
* Fixed: a PDF whose text survived extraction as invalid UTF-8 lost all of it. The fallback for a failed unicode whitespace pass ran against an empty string rather than against the extracted text, so the document was reported as having no text layer at all rather than indexing partially.
* Fixed: the Diagnostics screen could take itself down on exactly the sites that needed it. The PDF eligibility figure tested up to 500 files, each costing two unindexable `LIKE` scans in the default linked mode, in a single page load — enough to exhaust the execution limit on a large media library and leave a white screen on the only page from which the setting can be corrected. Both the PDF and image figures now test a bounded sample and say so in the label.
* Fixed: every visitor search full-scanned the documents table looking for contents pages. This was the last unbounded query left on the visitor path after 0.9.7 cached the corpus statistics, and the fix is a single index.
* Fixed: orphan-term pruning ran on every post save, trash and delete — a full anti-join across the entire terms and postings tables, which on a large index made editing a long post a multi-second write and an import considerably worse. It bought nothing: a term with no postings is invisible to search. The prune now runs on the paths that already walk the whole index.
* The `/ask` endpoint declares a length bound at the route, so an oversized request body is rejected before `wp_strip_all_tags()` and a unicode regex have run over all of it.
* The session identifier is now stored on a visitor's device only when query logging is switched on. PECR regulation 6 covers all storage on terminal equipment, not only cookies, and the identifier exists to group queries in the log for tuning rather than to deliver the search itself — so with logging off there is nothing to group and nothing is stored.
* Ships `languages/mbr-isa.pot`. `load_plugin_textdomain()` pointed at a directory that did not exist, so all 283 translatable strings were permanently inert. Fixing this also closed a related fault: the `wp_kses()` allowlist on one translatable admin string permitted an `onclick` attribute, which a malicious or compromised translation could have used to run script in an administrator's session.
* The update check no longer sends the site's PHP version, locale and installed plugin version to GitHub. The manifest is a static file that ignores them.
* Uninstalling a network-activated copy now cleans every site in the network rather than only the current one.
* Added the `Update URI:` header, so a WordPress.org plugin claiming this slug cannot serve an update to this one.
* Housekeeping from the audit: feedback statistics and query-log retention no longer mix the database server's clock with WordPress's site-local time, constructor parameters use explicit nullable types (deprecated implicitly in PHP 8.4), and a `\u2014` escape in a single-quoted string no longer prints literally in WP-CLI.

= 0.9.8 =
Follow-up to the 0.9.7 code review, plus a long-standing cosmetic fault. No schema change and no reindex needed.

* The PDF reference scan now applies the same visibility decision as everything else. Whether a published post mentions the file's path is a SQL question; whether that post is publicly readable is not, because `mbr_isa_can_index_post` is arbitrary PHP and cannot be expressed as a WHERE clause. A members-only page that the filter correctly kept out of the index therefore still counted as evidence that a PDF it links to was published, and the file's full text was indexed and served to anonymous visitors — the same access-control gap, one level down. Candidate posts are now retrieved and re-tested through `is_publicly_readable()` in both the post-content and post-meta passes, bounded by a candidate cap that fails closed and adjustable with the new `mbr_isa_pdf_reference_candidates` filter.

The panel's four sections and the two controls inside the form row now zero their margins, scoped deeply enough to outrank a theme rule targeting forms inside the content wrapper.

= 0.9.7 =
Security and scalability release, prompted by an external code review. None of the security work needs a reindex; the contents-page and chunking fixes below are applied during indexing, so a full reindex is needed for those.

* Widened what counts as publicly readable. Published and unprotected is no longer sufficient on its own: the post type must also be viewable on the front end, and a new `mbr_isa_can_index_post` filter lets membership and access-control plugins veto a post the indexer cannot otherwise know is restricted. The filter is deny-only — it cannot unlock a draft or a protected post.
* Results are now revalidated at search time. Every result is re-tested against the live post before it leaves the server, so a page that was legitimately indexed and has since become private, protected, restricted or deleted is discarded rather than served. This closes the whole class of stale-index disclosure, including the window on sites upgrading from an older version with an index built under narrower rules.
* The indexer no longer trusts the settings screen for a security decision. Post-type visibility is verified independently at index time, so a type that is enabled but has since been re-registered as private cannot be swept back in.
* A PDF's contents are only treated as published if the thing linking to it is itself reachable. The reference scan previously accepted a link from any post type other than a revision or attachment, including types with no front end at all.
* Stale index rows are cleaned up in the background after upgrading, and on demand with `wp mbr-isa purge` (`--dry-run` to preview). Housekeeping rather than a security control — nothing is exposed while it is pending.
* Search no longer recalculates field lengths across the entire postings table on every visitor query. Only documents containing a query term are loaded, and corpus statistics are cached until an index write invalidates them. Scores are unchanged.
* Feedback ratings are one per query. A token stays valid for an hour and is not consumed by use, so a caller holding one could previously resubmit repeatedly and move the statistics. A lost response on a rating that actually succeeded is now reported as success rather than as a failure.
* Update packages are verified against a SHA-256 published in the update manifest before WordPress unpacks them. Backward compatible: a manifest with no `checksum` key updates exactly as before. Define `MBR_ISA_REQUIRE_SIGNED_UPDATES` to refuse unverifiable packages.
* Full reindex asks the host for more execution time and memory. WP-CLI remains the reliable route on large sites.
* Fixed contents-page detection, which never fired on documents whose contents entries carry no full stop -- "3 How it works" rather than "3. How it works", which is how this plugin's own user guide is set. Such a page registered no entries at all, so it was neither demoted nor stood aside for the chapter it lists. Both forms are now recognised, and the run of entries is measured on its own rather than averaged across the whole passage, so a short contents list sharing a chunk with ordinary prose is still caught. Decimals remain excluded, so settings tables are unaffected. Stored on the row at index time -- existing documents keep their old answer until reindexed.
* Fixed: the chunk overlap handed a contents page's opening entries to the chunk before it. Overlap exists so a sentence straddling a boundary survives whole in one chunk -- but a contents run copied into a neighbour gives those chapter titles to a passage that is mostly ordinary prose, which is therefore not detected as a contents page, not demoted, and free to represent the document. Searching a chapter title returned the contents listing while the correctly-flagged chunk sat demoted beside it. A contents run now gets a chunk of its own, with no overlap taken across its edges.
* Fixed: the contents-page substitution could only draw a replacement from the candidate pool -- the top 50 scoring chunks across the whole index. That is ample for a distinctive term, and fails precisely where a contents page is most tempting: search words that appear in every document and the pool fills with short dense passages, the contents chunk among them, while the chapter that should have replaced it ranks 60th and is never considered. The substitution now looks across every chunk that matched, querying only for documents actually facing the problem.
* Fixed: the PDF extractor inserted a space after every text-showing operator, inventing word breaks that the document does not contain. Two Tj operators with no positioning between them continue at the current point, so the glyphs are adjacent and no space belongs there -- but producers split strings constantly, for an escaped entity, a font switch, an encoding change mid-word. A heading reading "What's new" could therefore be indexed as "What ' s new" and never found by anyone quoting it. Separation is now the business of the operators that move the cursor, Tm included, which previously supplied none. Requires a reindex of any PDF.
* Fixed: a quoted search opened its snippet in the wrong place. A phrase is tokenised like any other query, so "How it works" reached the snippet builder as the single stem "work" once stopwords were dropped -- and opened on whichever occurrence of "work" scored best. The deep-link builder shares that helper, so PDFs opened at the wrong page too. The literal phrase is now located first, falling back to term scoring only where the phrase is genuinely absent from the passage.
* Changed: the chat panel collapses towards the floating bubble when closed rather than fading in place. CSS only, and it honours prefers-reduced-motion.
* Changed: the footer credit links to the plugin's own page rather than the site root.

= 0.9.2 =
* **Added: PDF results now open near the matching passage rather than at the top of the page.** A link has always used `#page=N`, which scrolls the top of that page into view — so a passage halfway down the page left the visitor a screen above it, and on a dense page that meant most of a page of hunting. Links now carry a vertical target too, via the `view=FitH` open parameter.
* How the position is derived: the extractor reads the operators that move the text cursor but discards their operands, so no coordinates exist anywhere in the index. Instead the offset is estimated from how far through a page's words the passage begins, combined with the page height read from its `MediaBox` — new in this release. It assumes text is spread evenly down the page.
* That assumption fails on pages with figures, tables or short closing paragraphs, so the estimate is biased upward by about a fifth of a page. The passage therefore lands at or below the top of the view, never above it: the visitor scrolls down a little, in the same direction they would have scrolled before, just far less far.
* Pages rotated 90 or 270 degrees are measured on their rotated height, and a MediaBox inherited from the page tree is followed. Where a height cannot be resolved for every page, no offsets are stored and links behave exactly as they did before.
* Passages already near the top of a page, and matches falling on a later page than the chunk began on, get no offset — the page top is already correct and the reader's zoom is left alone.
* Added: `pdf_link_position` (default true) to switch the behaviour off. `view=FitH` forces a fit-width zoom, which the open-parameter syntax gives no way to avoid, so some sites may prefer the plain page link.
* **Schema v5, and a full reindex is required.** The offset is written per passage at index time. The new column defaults to zero, which means "no offset", so existing rows keep the old page-top behaviour until rebuilt. Nothing breaks in the meantime — the improvement simply does not appear. Run `wp mbr-isa reindex`.

* **Added: quoted phrase search.** Wrapping a query in quotes — `"opening hours"` — searches for that exact run of words instead of the words separately. Straight and curly quotes are both understood, single and double.
* A quoted query skips intent matching, so a phrase sharing a word with an intent trigger no longer gets the canned answer instead of the search. Synonym expansion is skipped too, since substituting words is the opposite of what an exact search asks for.
* How it works: the index holds no positional data, so the stems find candidate passages and the stored passage text is then checked for the literal phrase. The check runs before chunks are collapsed to one row per document, so a phrase in a document's third chunk is still found when its first chunk scores higher. The candidate pool is widened in phrase mode, since most candidates get rejected.

Controlled by `intent_supplementary_results` (on by default) and `intent_supplementary_max` (default 3).

= 0.8.2 =
This release is a security and privacy pass, prompted by an external code review. Three of the fixes change what the plugin indexes or retains, so please read the first four entries before updating.

* **Fixed (important): password-protected posts were indexed in full.** A password-protected post keeps the status `publish`, and the indexer gated on status alone — so the entire body of a protected post was written to the index and served as search snippets to anonymous visitors, who never saw the password prompt. Indexing now requires both a published status and an empty password. Protecting a post removes it from the index immediately.
* **Fixed (important): PDF indexing could expose files never meant to be found.** With PDF indexing enabled, every PDF in the Media Library was indexed regardless of whether anything linked to it — including files uploaded to drafts, superseded documents and files uploaded and then forgotten. A new "Which PDFs" setting defaults to indexing only PDFs attached to a published, unprotected post of an indexed type. Choose "Every PDF in the Media Library" only if the whole library is intended to be public.
* **Action required: existing indexes must be rebuilt.** The two fixes above govern what *enters* the index; they cannot retract what an earlier version already put there. Until a full reindex runs, content indexed by 0.8.1 remains searchable. An admin notice will prompt for this and clears when the reindex completes.
* **Added: query log retention.** The cleanup hook had been cleared on deactivation since 0.6 but was never actually scheduled, so the query log grew without limit. A daily cleanup now runs, with a retention period configurable under Privacy on the Diagnostics screen (7 / 30 / 90 days, or keep indefinitely). New installs default to 30 days; sites upgrading are set to 90 days so there is time to review or export before anything is removed.
* Fixed: PDF text extraction had no bound on decompression. A small compressed stream inside an otherwise-legal PDF could expand to an arbitrary size in memory before any output limit applied — enough to exhaust the PHP process. Inflation is now capped per stream and budgeted across the document.
* Fixed: feedback ratings could be submitted against any recent query. Query IDs are sequential and one is returned with every answer, so the rating endpoint could be walked to corrupt the statistics. Ratings now require a signed token issued alongside the answer, tying a rating to the client that received it.
* Fixed: the rate limiter used a rolling expiry rather than a fixed window. Each request extended the window, so a visitor querying steadily — well within the configured limit — would accumulate a count that never reset and eventually be throttled. Windows are now derived from the clock and expire on schedule.
* Fixed: the rate limiter counted every visitor behind a reverse proxy or CDN as one client, because it read `REMOTE_ADDR` only. Where a site sits behind a proxy, one busy visitor could throttle the whole site. Forwarded headers are now consulted, but only when explicitly trusted via the `MBR_ISA_TRUST_PROXY` constant or the `mbr_isa_trust_proxy` filter — those headers are client-supplied, so trusting them by default would let an attacker mint unlimited fresh buckets.
* Improved: the rate limiter uses an atomic increment where a persistent object cache is available, closing a race in which concurrent requests could each read the same count and let more traffic through than configured.
* Fixed: the first query of every session was logged with an empty session ID. The response carried a newly generated ID while the log was written with the original (absent) one, so the session index never saw the row that started the session.
* Changed: session IDs are generated with `random_bytes()` rather than `md5( uniqid() )`. Not a security token and still not treated as one, but no longer derivable from a timestamp.
* Changed: corrected the REST API documentation. The class described both endpoints as nonce-protected; the nonce was never verified and deliberately is not — it is printed into the page by `wp_localize_script()`, so a page cache serves one visitor's nonce to everyone, and enforcing it would break the widget on cached sites. The comments now describe what actually protects these endpoints.
* Fixed: plugin metadata. Corrected the update manifest's `tested` field and a `last_updated` date set in the future, and brought the bundled changelog up to date.

= 0.8.1 =
* Fixed: Search snippets from PDFs could be filled with rows of dots and stray page numbers, because table-of-contents leader runs were extracted as if they were text. Leader runs (dots, middots, bullets, dashes, underscores) and the page numbers they strand are now removed during extraction. This also stops them inflating a passage's length for BM25.
* Added: Contents pages are detected and demoted in ranking. A table of contents lists every heading in a document, which makes it the densest concentration of topic vocabulary in the file and a poor answer to any question. Such passages are scored at 40% so they surface only when nothing better matches, rather than being excluded — a visitor searching for a section title can still find it. Detection requires a run of ascending numbered entries with little connective prose, so numbered instructions and data tables are not affected. Tunable via `contents_score_penalty` in the settings option.
* Improved: Running headers and footers are removed from PDF text. A line such as "Acme Handbook · Version 2 · Page 14" repeats on every page; left in, it appeared inside search snippets and inflated the term frequency of the words it contained, making a document look more relevant to its own title than it should. Detection is by agreement — words most pages share at the same position, at the start or end of the page — so it adapts to any document without configuration. On a 37-page guide this removed around 3,000 characters of boilerplate.
* Improved: Snippets prefer prose over code. Technical documents often contain code samples, and a snippet opening mid-sample says nothing about whether the page answers the question. Where a term occurs both in code and in prose, the prose occurrence is used; where it occurs only in code, the snippet starts at the match and runs forward into the following prose rather than leading with the sample. Code remains fully indexed and searchable.
* Improved: PDF page links account for chunks that span a page boundary. A passage of a few hundred words routinely runs across two pages, so anchoring to the page the chunk began on landed roughly a third of results a page away from the text they matched. The page is now derived from where the match actually falls within the passage. On a 37-page guide this took page accuracy from 9/16 to 16/16 on a spread of realistic queries. No reindex required — the calculation happens at query time.
* Added: PDF results open at the matching page. PDF text is now extracted page by page — the page sequence is read from the document's page tree rather than assumed from file order — and each passage chunk records the page it begins on, so a PDF result links with `#page=N`. Honoured by Chrome, Edge, Firefox and Adobe Reader; viewers that ignore it simply open the file at the start. Documents whose structure cannot be read (object streams, damaged files) fall back to the previous whole-document extraction and link without a page number.
* Fixed: Contents-page cleanup could remove a legitimate page number from a running footer (a footer reading "Page 4" ahead of a numbered heading lost its digit). Page numbers are now only removed when a leader run introduced them.
* Added: Deep links to the matching passage. A search result for a post or page now links straight to the text that matched, using the Text Fragments standard (`#:~:text=`), so the visitor lands on the relevant passage with it highlighted rather than at the top of the page. Supported by Chrome 80+, Edge 83+, Firefox 131+, Safari 16.1+, Opera 67+ and Samsung Internet 13+; any browser that does not support it simply loads the page normally, so a link can never break. Fragments are anchored at the matched word, kept within a single sentence and a single block element (browsers will not match across block boundaries), and are skipped for PDFs, which use their own viewer parameters. Disable with `deep_link_results` in the settings option.
* Fixed: Stripping HTML joined adjacent block elements, so "<p>one</p><p>two</p>" was indexed as the single fabricated word "onetwo". Block boundaries are now preserved.
* Fixed: Markup could leak into page results as text — SVG icon attributes such as `fill="none" stroke="currentColor"` appearing in snippets, and words like `stroke` and `viewBox` becoming searchable terms. Passage chunking split the raw HTML, so a chunk boundary falling inside a tag left the following chunk starting mid-attribute with no opening angle bracket for strip_tags() to match. Content is now converted to plain text before it is chunked. Affects pages and posts; PDF text was never affected.
* Changed: Database schema version 4. The documents table gains `is_contents` and `page_number` columns. If you installed a pre-release 0.8.0 build, the upgrade runs on your next admin page load; run a full reindex afterwards.
* Improved: A full reindex now reports the number of documents and chunks actually written to the index, not the number of items attempted, and warns loudly if any failed. Previously a schema problem could make every write fail while the reindex still reported success.
* Added: WP-CLI support. `wp mbr-isa reindex` runs the full reindex from the command line, free of web-request time and memory limits — the recommended route for very large sites and large PDF libraries. `wp mbr-isa status` prints plugin version, schema version, index counts (documents, chunks, terms, postings), PDF indexing state, and the last full reindex time.
* Note: The CLI class is only loaded when WP-CLI is running; nothing changes on ordinary web requests.

= 0.7.1 =
* Fixed: PDF extraction could emit binary garbage into the index and search snippets. Embedded font programs (FontFile/FontFile2 streams) are Flate-compressed just like page content, inflate cleanly to binary, and could contain the bytes "Tj" by coincidence — passing the content-stream check and being parsed as text. Decoded streams must now look like text before they reach the parser, and the Tj/TJ check requires the operator in showing position (after a string or array close) rather than as a raw substring.
* Fixed: Long documents — large indexed PDFs especially — were unfairly buried in search results. BM25 length normalisation was applied per field but against the *total* document length, so a short title match on a long PDF inherited the length penalty of its entire body and could not outrank short pages. Each field is now normalised against its own length and its own corpus average (per-field lengths are derived from the existing postings data — no reindex required).
* Added: The Search Tester trace now reports the average field length per field, so the per-field normalisation can be inspected.
* Note: After updating, run a full reindex if any previously-indexed PDF showed garbled snippets, so its stored excerpt is rebuilt. The ranking fix itself needs no reindex.
